## Context

`horizon-blog` and `horizon-publish` are decoupled by design: the generator scores and writes posts; the publisher deduplicates and pushes them to Webflow. This separation is intentional — the generator has no CMS knowledge.

The problem is that deduplication only runs at publish time, after per-item scoring (one concurrent LLM call per item) and full post generation (one LLM call + web research per post). On slow news days or when a major story dominates for several days, the top-scored items are all about stories already published, and the pipeline produces zero new posts while having spent significant LLM budget.

The fix is to move duplicate detection earlier — before scoring — using Webflow as the only source of truth (no local state, no extra store). The generator must not import `WebflowPublisher` directly; it must go through an interface the publisher exposes. The publisher runner should use the same interface for consistency.

## Goals / Non-Goals

**Goals:**
- Remove already-published stories from the scoring candidate pool before any LLM scoring begins
- Expose a `create_publisher` factory from the publisher module so no code outside it imports `WebflowPublisher` directly
- Add a batch semantic dedup function (one LLM call for all candidates) to complement the existing per-post check
- Degrade gracefully: if Webflow is unconfigured or the query fails, proceed as today

**Non-Goals:**
- Replacing the publisher's existing two-pass dedup (it stays as the safety net)
- Storing any published-item state locally or in an external store
- Changing the scoring algorithm or gate logic
- Adding a new config field (existing `WEBFLOW_TOKEN` + `blog.publisher.collection_id` are sufficient)

## Decisions

### Decision: Filter before scoring, not after

Scoring is concurrent per-item LLM calls (`asyncio.gather` with one call per item). Filtering 10 duplicates out of 30 candidates before scoring saves 10 LLM calls. Filtering after scoring saves only generation calls (fewer, but the scoring cost is already spent).

**Alternatives considered:** Filter after scoring but before generation — saves generation calls but not scoring calls. Rejected because filtering earlier is strictly cheaper.

### Decision: One batch LLM call, not per-item

The existing `semantic_is_duplicate` checks one title against all existing posts — calling it per candidate would be N calls at the pre-filter stage. A batch variant sends all N source items (title + `ai_summary`) and all M Webflow posts (title + meta-description) in one call, returning a list of duplicate candidate indices.

**Alternatives considered:** Title normalisation only (no LLM) — fast and free but misses semantic duplicates where source titles and AI-generated blog titles differ (common case). Rejected.

### Decision: `create_publisher` factory in `publisher/__init__.py`, validation in caller

The factory is a thin constructor: `create_publisher(config: PublisherConfig, token: str) -> Publisher`. It returns a `WebflowPublisher` without validating `collection_id`. Each caller validates before calling — the publisher runner exits with a friendly error; the generator pre-filter skips silently.

**Alternatives considered:** Factory raises `ValueError` on empty `collection_id` — rejected because the two callers need different handling (hard exit vs silent skip), so centralising validation in the factory doesn't help.

### Decision: Fail open on Webflow query failure

If the pre-filter Webflow query raises an exception, log a warning and proceed with all items unfiltered. The publisher's existing dedup will still catch duplicates at publish time.

**Alternatives considered:** Fail hard and abort generation — rejected because a transient Webflow API error should not block the pipeline entirely.

### Decision: `batch_semantic_dedup` lives in `publisher/deduplicator.py`

It is dedup logic, not CMS logic. It belongs alongside `semantic_is_duplicate`. The generator importing from `publisher/deduplicator.py` is not a boundary violation — it is shared utility logic, not a Webflow-specific import.

## Risks / Trade-offs

- **Webflow query adds latency to `horizon-blog`** → mitigated by the fact that a single `list_items` call with a 14-day window is fast relative to the scoring LLM calls it replaces.
- **Batch LLM prompt grows large with many candidates** → `important_items.json` is typically 20–50 items; at this scale the prompt fits comfortably in context. If it grows beyond ~100 items, chunking would be needed.
- **Existing published posts lack `ai_summary` on the Webflow side** → the batch dedup compares source `ai_summary` against Webflow `meta-description`. Meta descriptions are generated by SEO and capture the story angle well enough for this check.
- **Generator now needs `WEBFLOW_TOKEN`** → this is already required by `horizon-publish`. In the GitHub workflow both commands run in the same environment, so no new secret management is needed.
